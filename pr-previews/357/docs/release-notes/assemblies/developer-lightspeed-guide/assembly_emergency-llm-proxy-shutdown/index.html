Shutting down the LLM proxy for emergency system isolation

During a security incident, stop all outbound large language model (LLM) traffic from developer integrated development environments (IDEs).

LLM proxy shutdown overview

The method that you use to shut down the large language model (LLM) proxy depends on how you deployed {ProductShortName}.

Warning

Perform these steps only under the direction of your security or incident-response team. Disabling the proxy immediately severs all in-progress LLM sessions for every connected developer without warning.
Centralized configuration mode

In Operator-managed or {ocp-short} deployments, the {ProductShortName} Operator manages the LLM proxy lifecycle. To disable the proxy, set kai_llm_proxy_enabled: false in the Tackle custom resource (CR). The Operator then terminates the proxy pod and does not re-create it.

Important

Do not directly scale the proxy Deployment object to zero replicas. The {ProductShortName} Operator reconciles managed resources and re-creates any manually scaled-down pods. To disable the proxy permanently, edit the Tackle CR.
Standalone deployment

Standalone deployments do not have a central proxy component to disable. Each integrated development environment (IDE) connects directly to the configured public LLM endpoint. You must block this traffic at the corporate firewall or the network policy layer.

Disable the LLM proxy by using the {ocp-short} web console

To disable the LLM proxy in centralized configuration mode, edit the Tackle custom resource (CR) in the {ocp-short} web console.

Prerequisites

  • You are logged in to the {ocp-short} web console with the cluster-admin role or an equivalent role that grants write access to the {ProductShortName} namespace.

  • You have identified the namespace where {ProductShortName} is installed, for example, mta or openshift-mta.

Procedure

  1. In the {ocp-short} web console, switch to the Administrator perspective.

  2. Click Operators > Installed Operators.

  3. From the Project list, select the {ProductShortName} namespace, for example, openshift-mta.

  4. Click Migration Toolkit for Applications.

  5. Click the Tackle tab.

  6. Click the name of your Tackle instance, for example, mta.

  7. Click Actions > Edit Tackle.

  8. In the YAML editor, find the spec section and set the kai_llm_proxy_enabled field to false:

    spec:
  kai_llm_proxy_enabled: false

  9. Click Save.

    The Operator reconciles the change and terminates the proxy pod.

Verification

  1. Click Workloads > Pods.

  2. From the Project list, select the {ProductShortName} namespace.

  3. Verify that no pod with proxy in the name has a Running status.

Disable the LLM proxy by using the CLI

To disable the LLM proxy for scripted incident response or when the {ocp-short} web console is unavailable, use the OpenShift CLI (oc).

Prerequisites

  • You have installed the OpenShift CLI (oc).

  • You are logged in to the cluster with the cluster-admin role.

Procedure

  1. Patch the Tackle custom resource (CR) to disable the LLM proxy:

    $ oc patch tackle <tackle_instance_name> -n <mta_namespace> \
  --type=merge -p '{"spec":{"kai_llm_proxy_enabled":false}}'

    where:

    <tackle_instance_name>

    Specifies the name of your Tackle instance.

    <mta_namespace>

    Specifies the name of the {ProductShortName} namespace.

    For example, to disable the LLM proxy for the mta instance in the openshift-mta namespace, enter:

    $ oc patch tackle mta -n openshift-mta \
  --type=merge -p '{"spec":{"kai_llm_proxy_enabled":false}}'
    tackle.tackle.konveyor.io/mta patched
Verification

  • Verify that no proxy pods are running:

    $ oc get pods -n <mta_namespace> | grep proxy

    where:

    <mta_namespace>

    Specifies the name of the {ProductShortName} namespace.

    No resources found in mta namespace.

Validate that the LLM connection is terminated

After you apply either the centralized or standalone isolation procedure, confirm that outbound large language model (LLM) traffic is fully blocked.

Procedure

  • On the affected workstation, confirm that the LLM endpoint is unreachable:

    $ curl -v --max-time 10 https://api.openai.com/v1/models

    1. Verify that the command returns one of the following outputs, depending on your deployment mode:

  • In local or standalone deployment and in DNS-blocked environment, the connection is refused:

    * connect to <ip_address> port 443 failed: Connection refused
curl: (7) Failed to connect to api.openai.com port 443 after <time_in_ms> ms: Connection refused

    where:

    <ip_address>

    Specifies the IP address of the endpoint.

    <time_in_ms>

    Specifies the time elapsed in milliseconds.

Verification

  • Verify the expected output when isolation is active (centralized mode, DNS resolves but service is down)

    curl: (22) The requested URL returned error: 503

Expected behavior on developer workstations after proxy shutdown

Review the expected connection errors and behavior changes in the developer integrated development environment (IDE) to understand the impact of proxy shutdown.

A proxy shutdown causes the following behavior changes:

  • In-progress large language model (LLM) requests from an IDE client receive an immediate 503 Service Unavailable or connection refused error.

  • Developers cannot send further LLM requests until the proxy is re-enabled.

  • Standard IDE functionality, such as code editing, file navigation, and build tools, is not affected. Only the Developer Lightspeed AI assistant stops responding.

  • An error indicator appears in the Lightspeed panel of the IDE.

    The exact message depends on the IDE client, but it typically resembles the following:

    Error: Unable to connect to the LLM proxy service. Contact your administrator.
